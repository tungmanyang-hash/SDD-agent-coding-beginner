# Claude Build Prompt —— 晚餐選擇器

> 可直接複製到 Claude，並附上列出的文件與現有程式碼。既有專案的框架與指令以 repository 內容為準。

```text
你是資深產品工程師與前端工程師。請在既有專案中實作「晚餐選擇器」，目標是交付可實際操作的 POC，不是靜態 mockup。

## 唯一事實來源（依優先級）
1. PRD.md：產品目的、目標使用者、範圍與非範圍。
2. SRS.md：功能與非功能需求、Given / When / Then 驗收條件。
3. SAD.md：系統架構、資料模型、外部依賴與不可逆決定。
4. DESIGN.md：使用者流程、頁面結構、元件、互動、狀態、無障礙與 QA。
5. DESIGN-BOARD.md：視覺方向、版面優先級、token 與視覺參考。

文件衝突處理：不可自行猜測或擴大範圍。先列出衝突與最小可行的建議；PRD 的產品範圍優先，SRS 的可驗證行為優先於純視覺偏好。

## 工作方式
1. 先閱讀所有提供的文件與目前 repository 結構。
2. 在修改程式碼前，輸出：
   - 實作計畫（最多 8 步）；
   - SRS 需求編號 → 畫面 / 元件 / 資料欄位的追溯表；
   - 你發現的缺口、衝突與假設。
3. 若不影響 PRD 範圍，請採用合理且可逆的預設值並明確記錄；若會改變產品、資料、外部服務或部署方式，先停下來詢問。
4. 以小且可驗證的步驟實作，保留既有專案慣例；不要無故重寫設定檔、替換框架或引入大型依賴。

## 實作要求
- 完成 DESIGN-BOARD.md §6 的全部畫面：初始、有效輸入、loading、成功結果、empty / 無結果、error 與 disabled（若適用）。
- 所有 SRS 的 FR 都必須有可操作的使用者介面與可驗證結果；所有影響 UI 的 NFR 都必須落實。
- 依 DESIGN.md 的 token 建立集中式 theme（例如 CSS variables / design tokens）；避免在元件中重複硬編碼色彩、間距、字級。
- mobile-first；在 mobile、tablet、desktop 不可有水平溢出、不可截斷核心內容。
- 每一個互動元件皆可用鍵盤操作且具有可見 focus；表單有可見 label；錯誤不可只靠顏色傳達；可點擊目標至少 44 × 44 CSS px。
- 保留使用者輸入直到使用者明確清除或成功完成任務；失敗時提供可恢復路徑。
- 不使用未提供或未授權的圖片、品牌、商標或字型。缺少素材時，以 CSS、文字或通用圖示完成。

## 專案限制
- 技術堆疊：沿用 repository 既有框架、語言、格式化與測試工具；若目前沒有程式碼，先說明建議的最小堆疊與理由，取得確認後才初始化。
- 可新增的依賴：優先不新增；只有既有工具無法完成時才新增最小且必要的依賴，並說明理由。
- 資料與後端：不做登入、帳號、雲端同步、購物、料理教學或複雜個人化資料庫。當次輸入與選定方案可依 SAD 使用瀏覽器本機資料；不可上傳個人資料。
- 外部 API：替代方案最終可由 AI 服務產生，但目前未提供已設定的 API 或密鑰。不得假裝存在 API key、不得把密鑰寫入前端；未設定服務時，實作可替換的 service interface 與 deterministic demo fallback，使完整流程仍可操作。
- 部署環境：靜態網站即可；不假設有後端或特定雲端服務。

## 驗證與交付
完成後請：
1. 執行並回報現有的 lint、typecheck、test、build 指令；若沒有測試，為核心邏輯補上最小的自動化測試，或清楚說明原因。
2. 依 DESIGN.md §7 逐項完成手動 Design QA。
3. 回報：修改檔案清單、需求追溯表、驗證結果、已知限制，以及所有尚未確認的假設。
4. 不要宣稱未實際執行的檢查已通過。
```
